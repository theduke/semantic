## 2. Claude Code

### 2.1 Process launch

The official TS SDK does not speak a network protocol; it spawns the `claude`
binary and talks over stdio. The exact argument prefix it uses (from `sdk.mjs`):

```
claude --output-format stream-json --verbose --input-format stream-json \
       [--include-partial-messages] [--include-hook-events] [--replay-user-messages] \
       [--model M] [--effort low|medium|high|xhigh|max] [--max-turns N] [--max-budget-usd X] \
       [--permission-mode MODE] [--allow-dangerously-skip-permissions] \
       [--permission-prompt-tool NAME | --permission-prompts host|none] \
       [--resume ID | --continue] [--fork-session] [--session-id UUID] [--no-session-persistence] \
       [--mcp-config JSON|FILE...] [--strict-mcp-config] \
       [--tools LIST] [--allowedTools ...] [--disallowedTools ...] [--add-dir ...] \
       [--agents JSON|FILE] [--agent NAME] [--json-schema JSON] [--thinking adaptive|disabled] \
       [--max-thinking-tokens N] [--betas ...] [--plugin-dir ...] [--setting-sources user,project,local]
```

Notes:

* `-p/--print` plus `--output-format stream-json` **requires `--verbose`** to emit
  the full event stream (the SDK always passes it).
* Full flag list verified with `claude --help` (2.1.286). Relevant extras that
  exist in this version: `--bare` (skip hooks/LSP/CLAUDE.md discovery; auth only
  via `ANTHROPIC_API_KEY`/`apiKeyHelper`), `--safe-mode`, `--restricted`,
  `--system-prompt`, `--append-system-prompt`, `--exclude-dynamic-system-prompt-sections`
  (cache friendliness), `--fallback-model`, `--forward-subagent-text`,
  `--prompt-suggestions`, `--settings <file|json>`, `--worktree`, `--name`.
* `--permission-prompts host|none`: with `host` (default) the SDK host answers via
  control_requests (or a `--permission-prompt-tool` MCP tool); `none` auto-denies
  anything that would prompt.
* The SDK sets `CLAUDE_CODE_ENTRYPOINT=sdk-ts` and `CLAUDE_AGENT_SDK_VERSION`.
  Hosts should set a distinct entrypoint/client-app env so telemetry is
  attributable (`CLAUDE_AGENT_SDK_CLIENT_APP` exists).
* Config dir: `CLAUDE_CONFIG_DIR` (default `~/.claude`); sessions live in
  `$CONFIG/projects/<encoded-cwd>/<session-id>.jsonl` where the encoded cwd
  replaces every non-alphanumeric character with `-` (long names truncated and
  hashed) (docs: code.claude.com/docs/en/agent-sdk/sessions).

### 2.2 Framing and message directions

Every line on stdin and stdout is one JSON object with a top-level `type`.

Host to CLI (stdin):

| `type` | Purpose |
| --- | --- |
| `user` | A user message: `{"type":"user","message":{"role":"user","content":<string|blocks>},"parent_tool_use_id":null,"session_id":"...","uuid":"...","priority":"now|next|later","shouldQuery":true,"origin":{"kind":"human"}}` |
| `control_request` | Host-initiated request (initialize, interrupt, set_model, ...) |
| `control_response` | Answer to a CLI-initiated `control_request` (can_use_tool, hook_callback, mcp_message, elicitation) |
| `control_cancel_request` | Withdraw a pending request: `{"type":"control_cancel_request","request_id":"..."}` |
| `keep_alive` | Heartbeat (either direction; ignore on receive) |

CLI to host (stdout), the `SDKMessage` union (schema: `sdk.d.ts` `SDKMessage`):

| `type` / `subtype` | Meaning |
| --- | --- |
| `system` / `init` | Session metadata, emitted at the **start of each turn** (not only once): `session_id`, `model`, `cwd`, `tools[]`, `mcp_servers[{name,status}]`, `slash_commands[]`, `skills[]`, `plugins[]`, `agents[]`, `permissionMode`, `apiKeySource`, `claude_code_version`, `output_style`, `capabilities[]` (feature-detect strings, e.g. `interrupt_receipt_v1`, `interrupt_cancel_queued_v1`), optional `effort`, `fast_mode_state` |
| `assistant` | Complete assistant message (Anthropic `BetaMessage` shape: `id`, `model`, `content[]` of `text`/`thinking`/`tool_use`/..., `stop_reason`, `usage`). Fields: `parent_tool_use_id`, `uuid`, `session_id`, `error` (see below), `aborted`, `supersedes[]`, `subagent_type`, `task_description`, `user_message_uuid(s)` |
| `user` | Echoed/synthesized user-role messages: mainly **`tool_result` blocks** produced after tool execution, with structured `tool_use_result`; also replayed human input when `--replay-user-messages` |
| `stream_event` | Only with `--include-partial-messages`. Wraps one raw Anthropic stream event in `event` (`message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`); has `parent_tool_use_id`, `ttft_ms` |
| `result` / `success` or `error_during_execution`/`error_max_turns`/`error_max_budget_usd`/`error_max_structured_output_retries` | **Exactly one per turn; the turn-complete signal.** `result`, `is_error`, `num_turns`, `duration_ms`, `duration_api_ms`, `total_cost_usd` (cumulative across turns in streaming-input sessions), `usage` (main loop, per turn), `modelUsage{model:{inputTokens,outputTokens,cacheReadInputTokens,cacheCreationInputTokens,costUSD,contextWindow,maxOutputTokens,...}}` (cumulative, includes subagents), `permission_denials[]`, `stop_reason`, `terminal_reason`, `structured_output`, `queued_turn_count`, `session_id` |
| `system` / `session_state_changed` | `state: idle|running|requires_action`. Informational messages may follow `result`, so "turn done" = `result`, "session quiescent" = `idle` |
| `system` / `status` | `status: compacting|requesting|null`, `permissionMode`, compaction result |
| `system` / `compact_boundary`, `api_retry`, `commands_changed`, `background_tasks_changed`, `informational`, `notification`, `permission_denied`, `files_persisted`, `memory_recall`, `thinking_tokens`, `model_refusal_fallback`, `model_refusal_no_fallback`, `worker_shutting_down`, `local_command_output`, `plugin_install`, `elicitation_complete`, `control_request_progress`, `mirror_error` | Diagnostics/UX; most can be ignored by a first implementation. Unknown subtypes must be tolerated |
| `system` / `task_started`, `task_progress`, `task_updated`, `task_notification` | Subagent/background task lifecycle (`task_id`, `tool_use_id`, `subagent_type`, `description`, `usage{total_tokens,tool_uses,duration_ms}`, `status completed|failed|stopped`) |
| `system` / `hook_started`, `hook_progress`, `hook_response` | Only with `--include-hook-events` |
| `rate_limit_event` | `rate_limit_info{status allowed|allowed_warning|rejected, resetsAt, rateLimitType five_hour|seven_day|..., utilization, overage*}` (claude.ai subscription users) |
| `tool_progress`, `tool_use_summary`, `auth_status{isAuthenticating,...}`, `prompt_suggestion`, `active_goal`, `conversation_reset` | Misc UX |
| `control_request` / `control_response` / `control_cancel_request` | Control protocol, section 2.4 |
| `transcript_mirror` | Present in the SDK reader; only relevant to session-store mirroring |

`SDKAssistantMessageError` values on `assistant.error`: `authentication_failed`,
`oauth_org_not_allowed`, `account_on_hold`, `billing_error`, `rate_limit`,
`overloaded`, `invalid_request`, `model_not_found`, `server_error`,
`max_output_tokens`, `unknown`. This is the best source for classified errors.

### 2.3 Streaming content and subagents

* **Without** `--include-partial-messages` each content block arrives as a
  complete `assistant` message (one message may hold a single block; several
  assistant messages share a `message.id`).
* **With** it, `stream_event` frames carry token-level deltas (`text_delta`,
  `thinking_delta`, `input_json_delta` for tool args). Tool-use input only
  becomes parseable at `content_block_stop`; the final `assistant` message still
  follows and is the canonical record. t3code always enables partial messages.
* `parent_tool_use_id` is `null` for main-agent frames and holds the `Task`/`Agent`
  tool_use id for frames produced inside a subagent. By default subagent
  text/thinking is **not** forwarded; `--forward-subagent-text` /
  `forwardSubagentText` turns it on. `system/task_*` messages are always the more
  reliable subagent lifecycle signal.
* Subagent tool is named `Agent` (older: `Task`); `AgentInput = {description,
  prompt, subagent_type?, model?, run_in_background?, name?, isolation?}`.
  Background agents keep running after an interrupt only if the host advertised
  `perTaskStopAffordance` in `initialize` and then uses `stop_task`.
* `TodoWrite` is an ordinary tool_use: input `{todos:[{content,status:
  pending|in_progress|completed,activeForm}]}`. Hosts map it to a plan/checklist
  (t3code: `claudeTodoSteps`).

### 2.4 Control protocol (bidirectional)

Envelope (schema: `SDKControlRequest`, `SDKControlResponse`):

```json
{"type":"control_request","request_id":"abc123","request":{"subtype":"...", ...}}
{"type":"control_response","response":{"subtype":"success","request_id":"abc123","response":{...}}}
{"type":"control_response","response":{"subtype":"error","request_id":"abc123","error":"message"}}
{"type":"control_cancel_request","request_id":"abc123"}
```

`request_id` is chosen by the sender (SDK uses random base36). Either side may
send control_requests. `control_cancel_request` tells the peer you no longer need
an answer (e.g. a pending `can_use_tool` after interrupt); no reply to the cancel.

Host to CLI requests (the `SDKControlRequestInner` union, subtype names):

| subtype | Purpose / notable fields |
| --- | --- |
| `initialize` | Must be first. `hooks{event:[matchers]}`, `sdkMcpServers[]` (names of host-hosted MCP servers), `sdkMcpServerConfigs`, `systemPrompt[]`, `appendSystemPrompt`, `systemPromptSnapshot`, `planModeInstructions`, `jsonSchema`, `agents{}`, `skills[]`, `toolAliases`, `title`, `promptSuggestions`, `agentProgressSummaries`, `forwardSubagentText`, `supportedDialogKinds[]`, `perTaskStopAffordance`, `excludeDynamicSections`. Response: `commands[]`, `agents[]`, `output_style`, `available_output_styles[]`, **`models[]`** (`value,displayName,description,supportsEffort,supportedEffortLevels,supportsAdaptiveThinking,supportsFastMode,supportsAutoMode`), **`account`** (`email,organization,subscriptionType,tokenSource,apiKeySource,apiProvider firstParty|bedrock|vertex|foundry|gateway|...`), `pending_permission_requests[]`, `pending_user_dialog_requests[]`, `hooks_applied`, `fast_mode_state` |
| `interrupt` | Abort the running turn. `cancel_queued?: bool` also drops queued user messages. Response (when `interrupt_receipt_v1`): `{still_queued:[uuid], cancelled?:[uuid]}`. The interrupted turn still emits a `result` (error subtype) |
| `set_permission_mode` | `mode`: `default`, `acceptEdits`, `bypassPermissions`, `plan`, `dontAsk`, `auto` |
| `set_model` | `model` string, or null/`default` to reset |
| `set_max_thinking_tokens`, `rename_session`, `set_color` | Session tweaks |
| `mcp_status`, `mcp_set_servers`, `mcp_reconnect`, `mcp_toggle`, `mcp_call` | Runtime MCP management |
| `get_context_usage`, `get_session_cost`, `get_usage`, `get_binary_version`, `get_settings`, `apply_flag_settings`, `update_settings` | Introspection/config |
| `list_models`, `reload_plugins`, `reload_skills`, `file_suggestions`, `read_file`, `seed_read_state`, `register_repo_root`, `rewind_files`, `background_tasks`, `stop_task`, `cancel_async_message` | Misc |
| `elicitation`, `request_user_dialog` | Actually CLI-initiated; see below |

CLI to host requests (host must answer with a `control_response`):

| subtype | When | Expected answer |
| --- | --- | --- |
| `can_use_tool` | Permission needed (and for `AskUserQuestion`, `ExitPlanMode`) | `PermissionResult` |
| `hook_callback` | A hook registered at `initialize` with a `callback_id` fired | hook output JSON |
| `mcp_message` | Traffic for an SDK-hosted MCP server (`server_name`, JSON-RPC `message`) | `{mcp_response: <jsonrpc>}` |
| `elicitation` | MCP server asked for user input (`mcp_server_name`, `message`, `mode form|url`, `requested_schema`, `url`, `elicitation_id`, `title`) | accept/decline/cancel result |
| `request_user_dialog` | Host-rendered dialog; only sent for `dialog_kind`s listed in `supportedDialogKinds` (fails closed otherwise) | dialog-specific |

`can_use_tool` request body (schema `SDKControlPermissionRequest`):

```json
{"type":"control_request","request_id":"r7","request":{
  "subtype":"can_use_tool","tool_name":"Bash","tool_use_id":"toolu_01...",
  "input":{"command":"rm -rf build","description":"Remove build dir"},
  "permission_suggestions":[{"type":"addRules","rules":[{"toolName":"Bash","ruleContent":"rm -rf build"}],
                              "behavior":"allow","destination":"localSettings"}],
  "blocked_path":null,"decision_reason":"...","decision_reason_type":"rule|mode|safetyCheck|classifier|...",
  "title":"Run command","display_name":"Bash","description":"...","agent_id":null,
  "classifier_approvable":true,"suppress_always_allow_rule":false,"default_to_no":false,
  "requires_user_interaction":false}}
```

Responses (schema `PermissionResult`):

```json
{"type":"control_response","response":{"subtype":"success","request_id":"r7","response":
  {"behavior":"allow","updatedInput":{"command":"rm -rf build"},
   "updatedPermissions":[{"type":"addRules","rules":[...],"behavior":"allow","destination":"localSettings"}],
   "toolUseID":"toolu_01...","decisionClassification":"user_temporary|user_permanent|user_reject"}}}
{"type":"control_response","response":{"subtype":"success","request_id":"r7","response":
  {"behavior":"deny","message":"User declined","interrupt":false}}}
```

Gotchas confirmed by docs/types:

* `updatedInput` must be echoed (before CLI v2.1.207 an allow without it was
  rejected). Passing a modified input is the supported way to sanitize.
* `PermissionUpdate` variants: `addRules|replaceRules|removeRules` (rules
  `{toolName, ruleContent?}`, `behavior allow|deny|ask`), `setMode`,
  `addDirectories|removeDirectories`; destinations `userSettings|projectSettings|
  localSettings|session|cliArg`. "Allow always" = echo a suggestion back.
* `can_use_tool` is **not** called for tools auto-approved by rules or by the
  mode (`acceptEdits`, `bypassPermissions`). For universal interception use a
  `PreToolUse` hook (`hook_callback`).
* With `dontAsk` anything not pre-approved is denied without a prompt; the CLI
  emits `system/permission_denied`.
* The callback may stay pending indefinitely (turn is parked in
  `session_state_changed: requires_action`). To survive host restarts use a
  `PreToolUse` hook returning the `defer` decision and resume later.
* The docs mention a dummy `PreToolUse` hook workaround for Python streaming
  mode to keep the stream open for `can_use_tool` (SDK implementation detail;
  a custom host controlling stdin does not need it, but keep stdin open for the
  whole session).

### 2.5 Permission modes

| Mode | Behaviour |
| --- | --- |
| `default` | Prompt for anything not allowed by rules |
| `acceptEdits` | Auto-approve file edits (and some fs commands); others prompt |
| `plan` | Read-only exploration; the model finishes by calling `ExitPlanMode` |
| `bypassPermissions` | No prompts; requires `--allow-dangerously-skip-permissions` or `--dangerously-skip-permissions`. Refused in `--restricted` |
| `dontAsk` | Never prompt; non-pre-approved calls are denied |
| `auto` | Classifier-based auto approval (`decision_reason_type: classifier`) |

(The local `--help` also lists `manual` as a value; the SDK type union is
`default|acceptEdits|bypassPermissions|plan|dontAsk|auto`.)

### 2.6 AskUserQuestion and ExitPlanMode

Both arrive as `can_use_tool` requests, not as separate protocol messages.

`AskUserQuestion` input (1-4 questions, 2-4 options each; unavailable inside
subagents; must be in `--tools` if you restrict tools):

```json
{"questions":[{"question":"How should I format the output?","header":"Format",
  "options":[{"label":"Summary","description":"Brief overview"},{"label":"Detailed","description":"Full explanation"}],
  "multiSelect":false}]}
```

Host answers with an `allow` whose `updatedInput` carries the original questions
plus an `answers` map keyed by the **question text** (value: selected label, or
labels joined with `", "`, or free text); optional `response` for a free-form
reply that dismisses the card:

```json
{"behavior":"allow","updatedInput":{"questions":[...],"answers":{"How should I format the output?":"Summary"}}}
```

`ExitPlanMode` input: `{"plan":"<markdown>"}` (+ deprecated `allowedPrompts`).
The user-visible plan is in `input.plan`. Two valid host strategies:

1. Treat as approval request: `allow` to leave plan mode (the CLI switches
   permission mode, reported through `system/status`/`init` `permissionMode`), or
   `deny` with feedback text so Claude revises.
2. t3code's strategy: capture the plan as a "proposed plan" artifact and
   **deny** with the message "The client captured your proposed plan. Stop here
   and wait for the user's feedback..." so the turn ends; the user later starts
   an implementation turn (possibly switching mode with `set_permission_mode`).
   t3code also resets the live process back to its opened permission mode after
   a denied ExitPlanMode.

### 2.7 Sessions: resume, fork, persistence

* `session_id` is in every message. Pin it up-front with `--session-id <uuid>` so
  the host owns the id (must be a valid UUID).
* `--resume <id>` continues a persisted session (cwd-independent lookup since CLI
  2.1.223 but file must exist on this machine); `--continue` = most recent in cwd;
  `--fork-session` with resume creates a new session id copying history;
  `resumeSessionAt` (SDK option; message uuid) truncates history at an
  assistant message, which t3code uses for rollback/rewind (and `forkSession()`
  SDK helper for branching).
* `--no-session-persistence` makes the session non-resumable.
* `listSessions()/getSessionMessages()` SDK helpers just read the JSONL files.
  A Rust host can parse `~/.claude/projects/**/*.jsonl` directly for history
  import, but that format is **not** a stable contract.
* File changes are not part of the session; use SDK `rewind_files` control request
  (file checkpointing, needs `enableFileCheckpointing` env opt-in) for undo.

### 2.8 MCP

* `--mcp-config <json|file>...` plus `--strict-mcp-config` (ignore user/project
  MCP). Format identical to `.mcp.json`: `{"mcpServers":{"name":{"type":"stdio",
  "command":"...","args":[],"env":{}}}}`, `type: http|sse` with `url`/`headers`.
* **SDK MCP servers** (in-process tools): the host lists names in
  `initialize.sdkMcpServers`, the CLI forwards JSON-RPC to the host via
  `mcp_message` control_requests. For a Rust host the practical alternative is
  to run a normal stdio/http MCP server (e.g. with `rmcp`) and pass it via
  `--mcp-config`; this is protocol-agnostic and works for Codex and ACP too.
* MCP tool names appear as `mcp__<server>__<tool>` in `tool_use` and in
  allow/deny rules. `CLAUDE_AGENT_SDK_MCP_NO_PREFIX` exists for SDK servers.

### 2.9 Hooks

`initialize.hooks` maps hook events to matchers with `callback_ids`; when fired
the CLI sends `hook_callback{callback_id,input,tool_use_id}` and expects hook
output JSON. Events (schema `HookEvent`): `PreToolUse`, `PostToolUse`,
`PostToolUseFailure`, `PostToolBatch`, `Notification`, `UserPromptSubmit`,
`UserPromptExpansion`, `SessionStart`, `SessionEnd`, `Stop`, `StopFailure`,
`SubagentStart`, `SubagentStop`, `PreCompact`, `PostCompact`, `PreModelSwitch`,
`PostModelSwitch`, `PermissionRequest`, `PermissionDenied`, `Setup`,
`TeammateIdle`, `TaskCreated`, `TaskCompleted`, `Elicitation`,
`ElicitationResult`, `ConfigChange`, `WorktreeCreate`, `WorktreeRemove`,
`InstructionsLoaded`, `CwdChanged`, `FileChanged`, `DirectoryAdded`,
`MessageDisplay`. Not needed for v1 of an abstraction except
`PreToolUse`-for-defer.

### 2.10 Auth, models, usage

* Auth detection without starting a session: `claude auth status` prints JSON
  (verified locally): `loggedIn`, `authMethod` (`claude.ai`, API key, ...),
  `apiProvider`, `email`, `orgName`, `subscriptionType`, `configDirectory`,
  `projectsDirectory`. Login: `claude auth login`, `claude setup-token`
  (long-lived token), env `ANTHROPIC_API_KEY`, Bedrock/Vertex/Foundry env.
  In-session: `initialize` response `account{...}` and init `apiKeySource`.
* Model list: `initialize` response `models[]` (preferred) or `list_models`.
  Aliases `opus`, `sonnet`, `haiku` (and newer) are accepted by `--model`.
* Usage/cost: per turn in `result.usage` and `modelUsage` (cumulative; read the
  latest result, never sum). `total_cost_usd` is an estimate (API-key list price),
  `costBasis` hints list vs managed. Subscription limits via `rate_limit_event`
  and `get_usage` (marked EXPERIMENTAL in the type).
* Context window: `get_context_usage` control request.

### 2.11 Process lifecycle and cancellation (Claude)

* Keep stdin open for the whole session; closing stdin ends the session (and
  kills background tasks as a "closed input" one-shot).
* Graceful interrupt: `interrupt`; the turn ends with a `result` (usually
  `is_error` with a cancellation `terminal_reason`) and the process stays
  usable. Hard stop: close stdin, wait, then SIGTERM/SIGKILL the process group.
* Cancel pending approvals when interrupting: the CLI may send
  `control_cancel_request` for `can_use_tool`; the host should also drop its
  UI prompt and respond `deny` (or not respond) accordingly.
* Queued user messages: sending a `user` message while a turn runs queues it
  (`priority: now|next|later`); `interrupt` reports `still_queued` uuids.
  `--replay-user-messages` echoes them for acknowledgement.
* stderr carries debug output only (`--debug-to-stderr` exists); structured
  errors come through `assistant.error` / `result`.

### 2.12 Rust client libraries for Claude (community, not official)

crates.io (checked 2026-10-03): `claude-agent-sdk-rs` 0.6.4 (tyrchen, 78 stars,
last push 2026-02, bidirectional streaming/hooks/custom tools), `cc-sdk` 0.8.1
(2026-04), `claude-code-sdk` 0.0.3, `claude-agent-sdk` 0.1.1 (claims
anthropics repo but the GitHub URL 404s; do not trust), `claude-code-acp-rs`
(ACP adapter). None are Anthropic-maintained. Given the small, stable envelope,
writing our own typed codec (serde tagged enums with an `Unknown(Value)` fallback
variant) is cheap and avoids lag behind new CLI versions.

## 3. OpenAI Codex (`codex app-server`)

### 3.1 Launch and transports

```
codex app-server                      # stdio JSONL (default, --listen stdio://)
codex app-server --listen ws://127.0.0.1:4500   # experimental WebSocket (/readyz, /healthz, token auth flags)
codex app-server --listen unix://[PATH]          # control socket; `codex app-server proxy` bridges stdio to it
codex app-server --listen off
codex app-server daemon ...                       # managed local daemon shared by CLI/IDE ("codex agents" browses it)
codex -c key=value ... app-server                 # config overrides (TOML values), --enable/--disable FEATURE
codex app-server --strict-config                  # error on unknown config keys
```

(Verified from `codex app-server --help`, 0.159.3.) t3code spawns
`codex ... app-server` over stdio.

**Wire format quirk (docs + t3code "patched protocol")**: messages are JSON-RPC 2.0
*without* the `"jsonrpc":"2.0"` member. A strict JSON-RPC library (e.g. one that
requires the field) will not interoperate; use a small custom codec.

Backpressure: when its queue is full the server rejects requests with JSON-RPC
error **`-32001` "Server overloaded; retry later"** (docs). Clients should retry
with exponential backoff.

### 3.2 Handshake

```json
{"method":"initialize","id":0,"params":{
  "clientInfo":{"name":"semantic","title":"Semantic","version":"0.1.0"},
  "capabilities":{"experimentalApi":true,
                  "optOutNotificationMethods":["turn/diff/updated"],
                  "requestAttestation":false}}}
{"id":0,"result":{ ...server info... }}
{"method":"initialized"}
```

`InitializeCapabilities` (schema): `experimentalApi` (opt in to experimental
methods/fields, otherwise "X requires experimentalApi capability" error),
`optOutNotificationMethods[]` (exact method names to suppress; useful to cut
volume), `extensions`, `requestAttestation`, `explicitGatewayOauth`,
`mcpServerOpenaiFormElicitation`. `initialize` must be the first request on a
connection, exactly once.

### 3.4 Core primitives

* **Thread** = conversation (persisted as a rollout JSONL under `~/.codex/`;
  `ThreadStatus`: `notLoaded|idle|systemError|active{activeFlags}`).
* **Turn** = one user request plus agent work; status `inProgress|completed|
  interrupted|failed`; `error{message, codexErrorInfo, additionalDetails}`;
  `codexErrorInfo` enum: `contextWindowExceeded`, `sessionBudgetExceeded`,
  `usageLimitExceeded`, `rateLimitExceeded`, `serverOverloaded`, `unauthorized`,
  `badRequest`, `sandboxError`, `tooManyDenials`, `internalServerError`,
  `httpConnectionFailed{httpStatusCode}`, `other`, ...
* **Item** (`ThreadItem` union, discriminated by `type`): `userMessage`,
  `agentMessage{text, phase, questions?}`, `reasoning{summary[],content[]}`,
  `plan{text}`, `commandExecution{command, cwd, status inProgress|completed|failed|
  declined, aggregatedOutput, exitCode, durationMs, commandActions[], processId}`,
  `fileChange{changes[{path,kind add|delete|update{move_path},diff}], status}`,
  `mcpToolCall{server, tool, arguments, result, error, status}`,
  `dynamicToolCall`, `collabAgentToolCall` (multi-agent), `subAgentActivity`,
  `webSearch`, `imageView`, `imageGeneration`, `sleep`, `enteredReviewMode`,
  `exitedReviewMode`, `contextCompaction`, `hookPrompt`, `functionCallOutput`.

### 3.6 Sandbox and approval policies

* `SandboxMode` (thread-level, kebab-case): `read-only`, `workspace-write`,
  `danger-full-access`.
* `SandboxPolicy` (turn-level, tagged `type`, camelCase): `dangerFullAccess`,
  `readOnly{networkAccess}`, `externalSandbox{networkAccess}`,
  `workspaceWrite{writableRoots[], networkAccess, excludeSlashTmp,
  excludeTmpdirEnvVar}`. `externalSandbox` = "the host already sandboxes me".
* `ApprovalsReviewer`: `user | auto_review` (alias `guardian_subagent`):
  auto-review routes approvals to a reviewer subagent. Always send it
  explicitly; omitting it on resume leaves the previous value sticky (t3code
  comment).
* Experimental: `permissions` / `permissionProfile/list` named profiles, `thread/settings/update`.
* Per-turn overrides (`approvalPolicy`, `sandboxPolicy`, `cwd`, `model`, `effort`,
  `summary`, `serviceTier`) apply to that turn **and subsequent turns**.

### 3.7 Steer, interrupt, plan mode, fork, revert

* `turn/steer {threadId, expectedTurnId, input[]}`: inject input into the
  running turn; fails if `expectedTurnId` is not the active turn (race-safe).
* `turn/interrupt {threadId, turnId}`: the turn ends with status `interrupted`
  (turn/completed notification). Pending approval requests are cancelled.
* Plan mode (experimental param on `turn/start`): `collaborationMode:
  {mode:"plan"|"default", settings:{model, reasoning_effort, developer_instructions}}`.
  The plan arrives as `plan` items / `item/plan/delta` / `turn/plan/updated`.
  `collaborationMode/list` enumerates modes.
* `thread/fork {threadId, lastTurnId?}`: new thread from history; `thread/revert`
  drops the last N turns of a *loaded* thread (t3code falls back to
  fork-then-rollback when history is paginated).
* `thread/resume {threadId, ...overrides}`: precedence history > path > id; if
  the thread is already running it rejoins. `excludeTurns:true` returns only
  metadata (cheap).
* `thread/inject_items`, `thread/compact/start`, `thread/shellCommand` (user `!cmd`).

### 3.8 Account, models, usage, config

* `account/read` returns `{account: null | {type:"apiKey"} | {type:"chatgpt",
  email, planType} | {type:"amazonBedrock"}, requiresOpenaiAuth: bool}`. This is
  the auth-detection call (t3code `CodexProvider` uses it). `codex login status`
  also works offline (prints "Logged in using ChatGPT").
* `account/login/start` (params: chatgpt browser flow, api key, device code, or
  host-supplied `chatgptAuthTokens`), `account/login/completed` notification,
  `account/updated`, `account/rateLimits/read` + `account/rateLimits/updated`.
* `model/list {limit, cursor, includeHidden}` returns `Model{id, displayName,
  description, hidden, defaultReasoningEffort, supportedReasoningEfforts[],
  inputModalities[], isDefault, serviceTiers, ...}` with cursor pagination.
* Token usage: `thread/tokenUsage/updated` carries `ThreadTokenUsage{total, last
  : {inputTokens, cachedInputTokens, outputTokens, reasoningOutputTokens,
  totalTokens, cacheWriteInputTokens}, modelContextWindow}`. No dollar cost in
  the protocol (subscription based); compute from a price table if needed.
* `config/read`, `config/value/write`, `config/batchWrite`,
  `configRequirements/read` (admin constraints).
* Per-thread config injection: `thread/start.config` (arbitrary config.toml
  overlay, e.g. `mcp_servers`) and `-c key=value` on the launch command. This is
  how to hand Codex our MCP server.

### 3.9 MCP

Codex is an MCP client: configured in `~/.codex/config.toml` `[mcp_servers.*]`,

### 3.10 `codex exec --json` (one-shot, brief)

`codex exec --json [--output-schema FILE] [--ephemeral] [-s read-only|workspace-write|

### 3.11 Schema generation and versioning

```
codex app-server generate-json-schema --out DIR [--experimental]
codex app-server generate-ts --out DIR [--experimental]
```

Produces per-message JSON Schema files plus bundles
(`codex_app_server_protocol.v2.schemas.json` etc., 275 v2 files). **The schema
is per binary version**: methods, enum values and fields move between releases
(example above). t3code vendors a generated copy
(`packages/effect-codex-app-server/src/_generated`) and uses a
`scripts/generate.ts`. For Rust: either (a) vendor the schema for a
min-supported version and use lenient decoding (`#[serde(other)]`, `Value`
for unknown), or (b) at runtime run `generate-json-schema` once per binary
version to detect incompatibility (diagnostics only; do not codegen at runtime).
Upstream Rust definitions live in `openai/codex/codex-rs/app-server-protocol`
(crate not published; `codex-app-server-protocol` 0.63.0 on crates.io is a stale
third-party fork, Dec 2025).

### 3.12 Pitfalls (Codex)

* Missing `jsonrpc` field; ids may be integers or strings; server-originated ids
  must be echoed with identical type.
* Notifications are very chatty; use `optOutNotificationMethods`.
* Items are streamed as `item/started` -> deltas -> `item/completed`; the
  completed item is authoritative (replace, do not append, accumulated deltas).
* `turn/start` response does not mean the turn finished: wait for `turn/completed`.
* An approval answered with `cancel` interrupts the turn; `decline` continues it.
* App-server also persists threads in the user's `~/.codex`; a host that wants
  isolation must set `CODEX_HOME` (t3code has `CodexManagedHome`/`CodexHomeLayout`).
* WebSocket/unix transports allow multi-client observation of one thread
  (`serverRequest/resolved`), but are marked experimental.

## 4. Agent Client Protocol (ACP)

### 4.1 What it is

Open JSON-RPC 2.0 protocol, originated by Zed (Aug 2025), now governed in
`github.com/agentclientprotocol` with JetBrains as co-sponsor. Roles: **Client**
(editor/host UI) and **Agent** (coding agent subprocess). Default transport is
stdio with newline-delimited messages (agent logs on stderr). All paths absolute,
line numbers 1-based, JSON keys camelCase, discriminators snake_case, `_meta`
extension bags, custom methods prefixed `_`.

Two live protocol generations:

* **v1** (`protocolVersion: 1`): stable, schema crate 1.10.2 (2026-10-01).
* **v2** (`protocolVersion: 2`): draft/alpha (schema 2.0.0-alpha.7 on
  2026-09-30). Clients send `protocolVersion: 2`; agents answer 2 if supported,
  else 1; both must keep v1 support per connection. t3code already sends
  `protocolVersion: 2` and bridges both in `packages/effect-acp/src/compat.ts`.

### 4.2 v1 method set (docs: protocol/schema)

Agent methods (client calls): `initialize`, `authenticate`, `logout`,
`session/new`, `session/load` (optional, history replay), `session/resume`
(optional, no replay), `session/prompt`, `session/cancel` (notification),
`session/set_mode` (deprecated), `session/set_config_option`, `session/list`,
`session/close`, `session/delete`; unstable: `session/fork`, `session/set_model`
(older), NES (`nes/*`), `document/*` notifications.

Client methods (agent calls): `session/update` (notification),
`session/request_permission` (required), `fs/read_text_file`,
`fs/write_text_file`, `terminal/create|output|wait_for_exit|kill|release`,
`elicitation/create` (+ `elicitation/complete` notification). Protocol level:
`$/cancel_request` (notification) cancelling an in-flight request (error code
`-32800`). Auth-required error code `-32000`.

### 4.3 Initialization

```json
{"jsonrpc":"2.0","id":0,"method":"initialize","params":{"protocolVersion":1,
  "clientCapabilities":{"fs":{"readTextFile":true,"writeTextFile":true},"terminal":true,
                        "elicitation":{...},"auth":{"terminal":true},"session":{"configOptions":{"boolean":{}}}},
  "clientInfo":{"name":"semantic","title":"Semantic","version":"0.1.0"}}}
{"jsonrpc":"2.0","id":0,"result":{"protocolVersion":1,
  "agentCapabilities":{"loadSession":true,
     "promptCapabilities":{"image":true,"audio":false,"embeddedContext":true},
     "mcpCapabilities":{"http":true,"sse":false},
     "sessionCapabilities":{"list":{},"resume":{},"close":{},"delete":{},"additionalDirectories":{}}},
  "agentInfo":{"name":"gemini-cli","title":"Gemini CLI","version":"0.62.0"},
  "authMethods":[{"id":"oauth-personal","name":"Log in with Google"}]}}
```

If `authMethods` is non-empty and the agent is not authenticated, `session/new`
fails with `-32000 auth_required`; the client then calls `authenticate
{methodId}` (v1 `id`; v2 `auth/login {methodId}`). Terminal auth methods
(`type:"terminal"`) let the client open a TTY running a login command (client
advertises `auth.terminal`).

### 4.4 Sessions

```json
{"method":"session/new","params":{"cwd":"/abs/path","additionalDirectories":[],
  "mcpServers":[{"name":"semantic","command":"/bin/semantic-mcp","args":["--stdio"],"env":[{"name":"K","value":"V"}]},
                {"type":"http","name":"api","url":"https://x/mcp","headers":[{"name":"Authorization","value":"Bearer t"}]}]}}
// result: {"sessionId":"sess_abc","modes":{"currentModeId":"ask","availableModes":[...]},
//          "configOptions":[{"id":"model","name":"Model","category":"model","type":"select",
//                            "currentValue":"x","options":[{"value":"x","name":"X"}]}],
//          "models": {...unstable...}}
```

* MCP servers are passed *per session* (stdio required; http optional by
  `mcpCapabilities.http`; sse deprecated, removed in v2). This is the portable
  way to hand every ACP agent our MCP server.
* `session/load` replays history as `session/update` notifications
  (`user_message_chunk`, `agent_message_chunk`, tool calls) **before** the
  response returns; `session/resume` reattaches without replay. In v2 both are
  `session/resume` with optional `replayFrom: {type:"start"}`.
* `session/list` (paged, optional cwd filter), `session/close`, `session/delete`
  are capability-gated.

### 4.5 Prompt turn and `session/update`

```json
{"method":"session/prompt","id":3,"params":{"sessionId":"sess_abc","prompt":[
   {"type":"text","text":"Fix the bug"},
   {"type":"resource_link","uri":"file:///abs/a.rs","name":"a.rs"}]}}
```

Content block types: `text`, `image`, `audio`, `resource_link`, `resource`
(embedded; needs `embeddedContext`). Client must respect `promptCapabilities`.

`session/update` notification `params.update.sessionUpdate` values:

| v1 | Payload | v2 equivalent |
| --- | --- | --- |
| `user_message_chunk`, `agent_message_chunk`, `agent_thought_chunk` | `content` block (+ `messageId` in newer schemas) | same, `messageId` required; plus whole-message upserts `user_message`, `agent_message`, `agent_thought` |
| `tool_call` | `toolCallId, title, kind, status, content[], locations[], rawInput, rawOutput` | merged into `tool_call_update` upsert; plus `tool_call_content_chunk` |
| `tool_call_update` | changed fields only | same (omit/null/value patch semantics) |
| `plan` | `entries[{content, priority high|medium|low, status pending|in_progress|completed}]` (whole list replaced each time) | `plan_update{planId,...}`, `plan_removed` |
| `available_commands_update` | slash commands `[{name, description, input{hint}}]` | same (+ commands in session responses) |
| `current_mode_update` | `currentModeId` | removed (use config option) |
| `config_option_update` | full `configOptions` | same |
| `session_info_update` | title, updatedAt | same |
| `usage_update` | context window used/size, optional cost | same |
| (unstable) `compaction_update`, `compaction_summary_chunk` | | |
| n/a | | `state_update{state: running|idle|requires_action, stopReason, error}`, `terminal_update`, `terminal_output_chunk` |

Turn end (v1): the `session/prompt` **response** carries `stopReason`:
`end_turn | max_tokens | max_turn_requests | refusal | cancelled`.
v2 changes this fundamentally: the response only acknowledges insertion
(`{messageId}`); completion is a `state_update: idle` with `stopReason` (adds
`error` stop reason). Rationale: queued messages, replay, multiple clients.
A host abstraction must therefore treat "turn finished" as an internal event
derived per protocol generation, not as a function return.

### 4.6 Tool calls and permissions

`kind`: `read | edit | delete | move | search | execute | think | fetch |
switch_mode | other`; `status`: `pending | in_progress | completed | failed`
(+ `cancelled` in v2). Tool `content[]` items: `{"type":"content","content":
<ContentBlock>}`, `{"type":"diff","path","oldText","newText"}` (v2 reworked into
`changes[]` + optional git `patch`), `{"type":"terminal","terminalId"}`.

```json
{"method":"session/request_permission","id":12,"params":{"sessionId":"sess_abc",
  "toolCall":{"toolCallId":"call_001","title":"Run cargo test","kind":"execute","rawInput":{"command":"cargo test"}},
  "options":[{"optionId":"allow-once","name":"Allow once","kind":"allow_once"},
             {"optionId":"allow-always","name":"Always allow","kind":"allow_always"},
             {"optionId":"reject-once","name":"Reject","kind":"reject_once"}]}}
// response:
{"id":12,"result":{"outcome":{"outcome":"selected","optionId":"allow-once"}}}
// or {"outcome":{"outcome":"cancelled"}}  (must be returned if the turn was cancelled)
```

The permission **options are agent-defined** (id/name/kind); the host maps them
to its own model by `kind`. v2 adds `title`, `description`, and a typed `subject`
(`tool_call` patch or `command{command,cwd}`).

### 4.7 Client-side fs and terminal (v1 only)

If the client advertises `fs.readTextFile/writeTextFile` the agent reads/writes
through the client (so unsaved editor buffers are visible); `terminal/create
{command,args,env,cwd,outputByteLimit}` returns `terminalId`; `terminal/output`
(returns `output`, `truncated`, `exitStatus`), `wait_for_exit`, `kill`, `release`.
Terminal embedding in tool call content shows live output. **Removed in v2**
(replaced by agent-owned display terminals plus MCP for client tools). A
headless host like ours should **not advertise** fs/terminal in v1 at all (the
agent then uses its own native tools), which also removes a large implementation
burden and a security surface. t3code's v2 path never advertises them.

### 4.8 Modes and config options

v1: `modes{currentModeId, availableModes[{id,name,description}]}` plus
`session/set_mode`. Superseded by `configOptions` (`session/set_config_option
{sessionId, configId, value}` returns the **full updated option list**; types
`select` (value string) and `boolean` (needs client cap); categories `mode`,
`model`, `model_config`, `thought_level`, `_custom`). Agents are asked to offer
both during transition; real agents differ (Gemini CLI offered only `modes` as
of t3code's comment). Hosts must support both: prefer a `category:"mode"`
config option, fall back to `set_mode`. Model switching: `category:"model"` option
(older agents: unstable `session/set_model`/`models` state).

### 4.9 Elicitation and agent extensions

`elicitation/create` (client method; form schema or URL mode) is the standardized
"ask the user" request; many agents still use extensions instead:
Cursor sends `cursor/ask_question`, `cursor/create_plan` (blocking) and
`cursor/update_todos`, `cursor/task`, `cursor/generate_image` (notifications);
Claude/Codex adapters rely on permission options and `_meta` (JetBrains AIR
extensions: `_meta.jetbrains.air.goal`, ...). Expect per-agent quirks; keep an
`extension handler` hook per adapter.

```rust
use agent_client_protocol::schema::v1::{ContentBlock, InitializeRequest, NewSessionRequest, PromptRequest,
```

  requests/notifications, builder with typed handlers, request correlation,
  cancellation `$/cancel_request`, MCP helpers via `-rmcp`). Caveats:
  (1) handler style is callback-based (`on_receive_*`), so an actor/channel
  adapter into our own event stream is needed; (2) v1 vs v2 types live in
  different modules (`schema::v1`, v2 behind an unstable feature), so one
  generation must be chosen per connection and normalized; (3) we need our own
  process supervisor on top (stderr capture, process-group kill, restart);
  `AcpAgent` is convenient but opaque; the lower-level `ByteStreams`/`Lines`
  transports allow plugging a self-managed `tokio::process::Child`;
  (4) fast-moving major versions. Alternative: depend only on
  `agent-client-protocol-schema` (types) and write a thin JSON-RPC pump; this is
  also what we need for Codex/Claude anyway.
* Other: `sacp` 11.0.0 (Symposium's extensions to ACP; third-party),
  `claude-code-acp-rs` 0.1.22 (Rust ACP *agent* for Claude).

### 4.12 Pitfalls (ACP)

* Agents differ widely in what they implement (modes vs configOptions, models,
  `session/load` vs `resume`, plan updates, usage). Capability negotiation is
  necessary but not sufficient; ship per-agent quirk tables (t3code has
  Gemini/Cursor/Grok/Devin/Antigravity-specific files).
* Auth flows are agent-specific (Google OAuth in a browser, API keys in env,
  terminal login). Surface `authMethods`; handle `-32000 auth_required` from
  `session/new`.
* v1 tool-call and permission shapes carry minimal structured info; `rawInput`
  is agent-defined; do not rely on kinds for safety decisions.
* `session/cancel` is a notification: the agent must still answer the pending
  `session/prompt` with `stopReason: cancelled`; pending `request_permission`
  must be answered `cancelled`. Some agents are slow/ignore it; t3code has
  `cancelBehavior: "wait-for-prompt"` and process-group termination as
  fallback.
* `session/load` replays history as updates; the host must dedupe versus its own
  stored history (or ignore replay).
* stderr is free-form logs; keep a bounded tail for diagnostics (t3code keeps
  the last 4 KiB and redacts home dir, bearer tokens, `sk-...`).

## 7. Recommendation

### 7.1 Which protocols to implement natively

Priority order:

1. **Generic ACP client** (largest reach, official Rust crate or schema crate).
   Covers Gemini, OpenCode, Cursor, Copilot, Grok, Qwen, Kimi, Goose, Cline, ...
   Support **v1 first**; add v2 behind the same internal event model once agents
   ship it (negotiation: offer 2, accept 1). Do not advertise `fs`/`terminal`.
2. **Claude Code native stream-json control protocol** (not through the ACP
   adapter): richer semantics (permission suggestions, `updatedInput`, AskUserQuestion,
   plan mode, cost/usage per model, rate limit events, subagent task events,
   interrupt receipts, resumeAt/fork). The wire format is small and stable
   (types in the SDK `.d.ts`); implement with serde enums + `Unknown` fallbacks.
3. **Codex app-server native** (JSON-RPC without `jsonrpc` header). Richer than
   `codex-acp`: items, steer, revert, goal, approvals with execpolicy
   amendments, token usage, account. Use `generate-json-schema` output from a
   pinned min version as the source of truth for serde types.
4. Optional later: OpenCode HTTP server (richer than ACP: global SSE, fork),
   `codex exec --json` / `claude -p --output-format json` as degraded one-shot
   "headless" backends for batch/CI use, Cursor/Gemini headless stream-json
   (low value once ACP exists).

Rationale for native Claude/Codex over their ACP adapters: ACP v1 cannot express
cost per model, permission suggestions with persistence scope, multiple
question forms, steer/queued messages, rewind, rate limits, and adapters add a
Node dependency (`npx`) and version skew (`claude-agent-acp` bundles its own
Agent SDK/CLI). Keep ACP adapters as a fallback (`provider = acp:claude-acp`).

### 7.2 Common capability model (what the abstraction should expose)

Do not force a lowest-common-denominator event; use an internal event model
plus **capability flags** discovered at runtime.

```text
ProviderKind       = ClaudeCode | Codex | Acp{agent_id} | OpenCodeServer | ...
ProviderInfo       { kind, binary path, version, protocol_version, installed: bool }
Auth               { state: Authenticated{account, plan, method} | NeedsLogin{methods} | Unknown,
                     login: Option<LoginFlow {Browser|Terminal{cmd}|ApiKeyEnv|DeviceCode}> }
Models             Vec<ModelInfo{id, name, efforts[], context_window?, default?}>   // dynamic
Capabilities {     // per provider AND per session (negotiated)
   streaming_text, streaming_reasoning, streaming_tool_args,
   interrupt, steer_running_turn, queue_messages,
   resume_session, fork_session, rewind_to_message, list_sessions, history_replay,
   permission_modes: Vec<Mode>, set_mode_live, set_model_live, set_effort,
   approval_scopes: {once, session, persistent_rule},
   user_questions (structured, multi-choice), plan_proposal (ExitPlanMode-like), todo_plan,
   subagents, mcp_stdio, mcp_http, mcp_in_process, image_input, audio_input, resource_links,
   structured_output(json_schema), usage_tokens, usage_cost, rate_limits, sandbox_control,
   diff_events, terminal_output }
SessionConfig {    // desired state, applied at start and diffed live
   cwd, additional_dirs, model, effort, mode (Interaction: Default|Plan) , approval (Never|OnRequest|Untrusted),
   sandbox (ReadOnly|WorkspaceWrite{roots,network}|FullAccess), mcp_servers[], system_prompt_append,
   env, resume: Option<NativeSessionId>, fork_from: Option<(id, point)> }
```

Event model (what the UI/DB consumes). Use the Codex "item" shape as the basis
because it is the most explicit lifecycle and maps well from Claude content
blocks and ACP tool calls:

```text
SessionEvent
  SessionStarted{native_id, model, cwd, mode, tools?}
  TurnStarted{turn_id}
  Item{ id, turn_id, parent_item_id (subagent/tool nesting), kind, status: Pending|Running|Completed|Failed|Declined|Cancelled,
        data, started_at, updated_at }
     kind = UserMessage | AgentMessage | Reasoning | ToolCall{category: Shell|FileEdit|Read|Search|Fetch|Mcp{server,tool}|Subagent|Other, name, input(json), output} 
          | FileChange{path, kind, diff} | Plan{entries} | Todo{entries} | Notice{level}
  ItemDelta{ item_id, field: Text|Reasoning|ToolOutput|ToolInput, delta }
  Request{ id, kind: Approval{tool/command/file, options[{id,kind: AllowOnce|AllowSession|AllowAlways|RejectOnce|RejectAlways}], suggestion?}
                   | Question{questions[...]}
                   | PlanApproval{markdown}
                   | Elicitation{schema/url} }   // expects respond(id, answer)
  RequestResolved{id}                                // answered elsewhere/cancelled
  Usage{ turn_or_cumulative, input, output, cached_in, cache_write, reasoning_out, cost_usd?, context_window? }
  RateLimit{...}  ModeChanged  ModelChanged  ConfigOptionsChanged  CommandsChanged
  TurnCompleted{turn_id, outcome: Completed|Interrupted|Failed{class: Auth|RateLimit|Overloaded|ContextOverflow|Refusal|Sandbox|Other}|MaxTurns|Budget, stop_reason}
```

Commands: `start/resume/fork`, `send_turn(inputs, overrides)`, `steer`, `interrupt`,
`respond(request_id, answer)`, `set_mode/model/effort`, `close`, `list_sessions`,
`rewind`. Everything async; a session is an actor owning the child process and
exposing `Stream<SessionEvent>` plus a command channel.

Mapping cheat-sheet:

| Concept | Claude stream-json | Codex app-server | ACP v1 |
| --- | --- | --- | --- |
| Turn start | send `user` msg | `turn/start` | `session/prompt` |
| Turn end | `result` msg | `turn/completed` | prompt response `stopReason` (v2: `state_update idle`) |
| Text delta | `stream_event content_block_delta text_delta` | `item/agentMessage/delta` | `agent_message_chunk` |
| Reasoning | `thinking_delta` | `item/reasoning/*Delta` | `agent_thought_chunk` |
| Tool item | `tool_use` / `tool_result` blocks | `item/started|completed` typed items | `tool_call` / `tool_call_update` |
| Approval | `can_use_tool` | `item/*/requestApproval` | `session/request_permission` |
| Question | `can_use_tool` AskUserQuestion | `item/tool/requestUserInput` | `elicitation/create` or agent extension |
| Plan proposal | `ExitPlanMode` tool | `plan` item + `collaborationMode` | `plan` update / `cursor/create_plan` / mode switch |
| Todo/plan list | `TodoWrite` tool | `turn/plan/updated` | `plan` update |
| Interrupt | `interrupt` control_request | `turn/interrupt` | `session/cancel` |
| Steer | queue a `user` msg (`priority:"now"`) | `turn/steer` | not in v1 (v2 queued messages) |
| Mode | `set_permission_mode` | per-turn `approvalPolicy`+`sandboxPolicy`+`collaborationMode` | config option category `mode` / `set_mode` |
| Model | `set_model` / `--model` | per-turn `model` | config option category `model` |

Permission policy abstraction: our own `ApprovalPolicy{Never|OnRequest|Untrusted}`
x `Sandbox{ReadOnly|WorkspaceWrite|Full}` x `Interaction{Default|Plan}` should be
**compiled per provider** (Claude to a `permissionMode`+tool allowlist; Codex to
`approvalPolicy`+`sandboxPolicy`; ACP to a mode/config option chosen by `kind`),
as t3code's `permissionModeForClaudeRuntimePolicy` and Codex
`runtimeModeDefaults` do. Be explicit that some combos are unrepresentable
(Claude has no OS sandbox policy; ACP agents often only have 2-3 opaque modes)
and report the effective mode back (`SessionStarted.effective_policy`).

### 7.3 Suggested crate layout

```
agent_core      // traits + SessionEvent/Command/Capabilities types; no I/O (data-model-first)
agent_jsonl     // child process supervisor: spawn, process group, stdin writer, line reader w/o max length,
                //   stderr ring buffer + redaction, exit/kill escalation, restart policy
agent_claude    // stream-json codec (serde enums + Unknown), control-request router, mapping -> core events
agent_codex     // app-server codec (no jsonrpc field), id routing, schema snapshot, mapping
agent_acp       // wraps agent-client-protocol (or schema crate): v1/v2 normalization, per-agent quirk table
agent_registry  // discover installed binaries, versions, auth state, ACP registry download+sha256
agent_testkit   // scripted fake agent speaking each protocol over pipes (record/replay NDJSON fixtures)
```

Make protocol codecs pure `fn(line) -> Event`/`fn(Command) -> bytes` plus a thin
async driver, so each can be tested with recorded transcripts (t3code has
`*.testkit.ts` and `replay.ts` for the same purpose). Record real transcripts from
each CLI version as golden fixtures.

### 7.4 Pitfalls and mitigations

1. **Versioning / schema drift.** Claude CLI auto-updates (new system subtypes
   weekly; capabilities list for feature detection); Codex enum values changed
   between releases (`on-failure` gone, `unlessTrusted` vs `untrusted`); ACP v1
   to v2 breaks the turn model. Mitigations: tolerant decoding everywhere
   (`#[serde(other)]` / keep raw `Value`), never fail a session on an unknown
   message, log them once; probe `--version` at start, gate on min versions, keep
   per-provider "known good range"; surface capability flags instead of version
   checks (Claude `capabilities[]`, ACP `agentCapabilities`, Codex
   `experimentalApi`); CI job that regenerates Codex schema from the latest
   binary and diffs.
2. **Process lifecycle.** Spawn in its own process group/session (`setsid`) and
   kill the group (agents spawn shells, MCP servers, `npx` wrappers). Tie child
   lifetime to the session (kill-on-drop, `PR_SET_PDEATHSIG` on Linux).
   Escalation: protocol-level cancel -> close stdin -> SIGTERM -> SIGKILL with
   timeouts. Detect crash (EOF on stdout) and fail all pending requests.
   Idle reaping; one process per session for Claude/ACP, one shared process with
   many threads for Codex (app-server multiplexes threads; watch cross-session
   notification routing by `threadId`).
3. **stderr.** Always drain stderr continuously (a full pipe blocks the child).
   Keep a bounded ring (4-64 KiB), redact secrets (home dir, bearer tokens,
   `sk-`, `ghp_`), attach to error events. Never parse it for control flow,
   except for last-resort auth/version hints.
4. **Large messages and framing.** NDJSON lines can be MBs (tool results, base64
   images, diffs, session history). Use a reader without a fixed line limit (or a
   very high one, with memory cap and truncation policy); avoid `lines()` with
   small default buffers; never split on `\n` inside JSON strings (JSON escapes
   newlines, so line framing is safe, but also strip a trailing `\r`). Handle
   ` / ` fine. Use `serde_json::from_slice` per line; skip
   non-JSON lines (some CLIs print banners/warnings to stdout, e.g. npm update
   notices from `npx` wrappers) instead of aborting.
5. **Request correlation and re-entrancy.** All three protocols are
   bidirectional: the agent sends requests *while your request is pending*.
   Reader task must dispatch concurrently; approvals/questions must not block
   the reader. Use per-id `oneshot` channels; ids are strings or ints (echo the
   exact JSON value); timeouts for control requests (Claude `initialize` can
   take seconds).
6. **Cancellation semantics.** Claude: `interrupt` -> `result` still arrives;
   queued messages survive unless `cancel_queued`; background subagents
   survive unless task-stop capability. Codex: `turn/interrupt`; approval
   `cancel` aborts the turn, `decline` does not. ACP: `session/cancel`
   notification; must answer pending permission with `cancelled`; agent still
   returns `stopReason: cancelled` (v2: idle state update). Model all of this as
   `interrupt()` returning when the *turn-complete* event arrives, with a timeout
   and escalation. Distinguish user-cancel from failure in `TurnCompleted`.
7. **Approvals must fail closed.** If the host disappears or the request times out,
   deny. Dedupe approvals across reconnects (Claude `pending_permission_requests`
   in the initialize response, Codex `serverRequest/resolved`). Never auto-allow
   by default; `bypassPermissions`/`danger-full-access` require explicit
   opt-in and a visible indicator.
8. **Auth detection.** Do it without a session when possible: `claude auth status`
   (JSON), `codex login status` / app-server `account/read`, ACP
   `initialize.authMethods` + `-32000` on `session/new`. Remember env-based
   auth (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`,
   `CURSOR_API_KEY`) and third-party providers (Bedrock/Vertex). Never print or
   persist tokens; login flows that need a browser/TTY should be launched by
   the host UI (open URL / run terminal), not by a headless child.
9. **State ownership and history.** Each CLI persists its own sessions (Claude
   JSONL, Codex rollouts, ACP agent-specific). Decide early: our DB is the system
   of record for the transcript (event sourcing from `SessionEvent`) and the
   provider session id is just a resume handle. Resume after the provider data is
   deleted must degrade (start fresh with a context handoff summary; t3code has
   `ContextHandoffService`). Provide isolation knobs (`CLAUDE_CONFIG_DIR`,
   `CODEX_HOME`) when the host must not touch the user's personal sessions.
10. **Env/config pollution.** User-level config (CLAUDE.md, hooks, MCP servers,
    Codex config.toml, skills) changes agent behaviour in ways the host cannot see.
    Offer a "hermetic" mode: Claude `--bare`/`--setting-sources`/`--strict-mcp-config`,
    Codex `--strict-config`, `CODEX_HOME`; and clearly report which sources are
    loaded (Claude init lists `plugins`, `skills`, `mcp_servers`).
11. **MCP delivery differs per protocol.** Claude `--mcp-config`, Codex
    `-c mcp_servers...`/`thread/start.config`, ACP `session/new.mcpServers`. Prefer
    exposing our own database tools as a local stdio/http MCP server and let the
    adapter inject it per protocol; avoid Claude SDK in-process MCP (needs the
    `mcp_message` tunnel).
12. **Usage/cost comparability.** Claude gives per-model USD estimates; Codex gives
    token counts only; ACP `usage_update` is optional. Store raw token counters
    and optional cost with a `basis` flag; do not sum cumulative counters.
13. **Security.** Treat all agent-provided strings (`decision_reason` may contain
    ANSI escapes; tool titles; permission option names) as untrusted when
    rendering. Validate paths from `file_change`/`locations` against the session
    cwd before opening files in our UI. WebSocket/unix transports for Codex need
    token auth; keep stdio.
14. **Windows.** Process groups, `.cmd` shims for `npx` agents, path encoding of
    Claude project dirs, no `setsid`. Plan for it even if Linux/macOS first.

### 7.5 Suggested first milestone

1. `agent_jsonl` supervisor + `agent_testkit` fake agents.
2. Codex adapter (cleanest model, schema-driven, no cost accounting) to settle the
   event/item model.
3. Claude adapter (control protocol, approvals, AskUserQuestion, plan).
